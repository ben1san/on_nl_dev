**作成日**: 2026年7月18日　**改訂日**: 2026年7月28日　**発表日**: 9月13日　**ステータス**: `01_requirements/Functional_Req.md`（現行FR番号）およびプロジェクト側`workspace/projects/landauers_furnace/docs/`と同期済み

## 0. この文書の位置づけ

`Functional_Req.md`の各FRに対し、「具体的に何を使って、どう実現するか」を定める。Must機能から着手し、Should/Could機能は実装コストとデモへのインパクトを見ながら着手判断する方針。

**発熱源（FR-06）・熱破壊回路（FR-12）の詳細設計は本書では扱わない**。コンデンサ対による回路原理の導出は[[architecture]]、部品表・実験手順は`components.md`が正であり、重複を避けるためそちらを参照する。本書はそれ以外のFR（FR-01, 03, 05, 07, 08, 10, 11, 14）の技術要件と、全体アーキテクチャ・BOM・リスクをまとめる。

## 1. システム全体アーキテクチャ

```
  記憶装置                    ┌─────────────────────────┐
  (USB/SD/外付SSD)  ───────▶│   忘却炉本体（黒い箱）      │
  （FR-01 投入口）            │  Raspberry Pi 4/5 が中枢   │
                             │                          │
                             │  ・記憶装置検知・レジスタ転写 │
                             │  ・QRNG取得(FR-03)        │
                             │  ・原本消去・点火(FR-05)    │
                             │  ・発熱/光/音の駆動         │
                             │    (FR-06,07,08)         │
                             │  ・感覚イベント配信(FR-11)   │
                             └───────────┬─────────────┘
                                         │ MQTT (Wi-Fi)
                                         │ 進行度・感覚イベントを配信
                         ┌───────────────┼───────────────────┐
                         ▼                                   ▼
             ┌───────────────────────┐         ┌─────────────────────────┐
             │ スマホ/タブレット/PC       │         │  発表用ノートPC             │
             │ （閲覧＋消去対象の選択・操作） │         │  シミュレーション演出        │
             │ 閲覧:MQTT/WS 操作:HTTP API│         │  （FR-14、筐体とは別体）     │
             └───────────────────────┘         └─────────────────────────┘

        （オプション・Tier2）
  忘却炉本体 ──UART/SPI──▶ Raspberry Pi Pico（FR-12：コンデンサ対によるレジスタを実装した場合の熱破壊回路。詳細は[[architecture]]）
```

- 中枢はRaspberry Piに一本化し、周辺の発熱・発光・発音・入出力デバイスをGPIO/I2C/SPI/USBで直結する構成
- **データ本体の入力はネットワークを経由しない**。記憶装置は投入口（USB-A／microSDスロット）に直接接続され、Piがブロックデバイスとして直接アクセスする。スマホ/タブレット/PCのWeb UIは、①消去対象の選択・実行確認（HTTPの制御API経由）、②儀式の進行状況・感覚イベントの閲覧、を担う。ファイルアップロード機能は持たせない
- 演出用のFR-14は意図的に「別体」とし、本体のRaspberry PiとはFastAPIのSSEで疎結合に接続する。FR-14が落ちても本体の儀式進行には影響しない
- MQTTブローカーはRaspberry Pi上でMosquittoを起動し、本体・（あれば）Pico制御用スクリプトが同一Wi-Fiネットワーク上でpublish/subscribeする。ブラウザは生のMQTT（1883番）を直接購読できないため、MosquittoにWebSocketリスナー（9001番）を追加し、`paho-mqtt.js`経由で購読させる

## 2. 機能ごとの技術仕様

### 2-1. Must機能（デモ当日、絶対に動かす）

#### FR-01 データ選択・投入（物理記憶装置限定）

- **入力方式**：投入口に挿された記憶装置（USBメモリ／SDカード／外付けSSD）を`pyudev`でホットプラグ検知し、`/dev/sdX`等のrawブロックデバイスとして直接アクセスする
- **UI方式**：React SPA（Vite + TypeScript）をFastAPI（uvicorn）が配信。消去対象の選択・実行確認のための制御API（挿入された記憶装置のファイル一覧取得／対象選択／実行確認）を持たせるが、ファイルアップロードのエンドポイントは持たせない。ファイル一覧はファイル名のみを返す
- **筐体側の物理UI**：操作ボタン類は設けない。「捧げる」所作は記憶装置を投入口へ挿す行為そのものが担い、投入・消去の確定はWeb UI上の二段階確認で行う
- **対応データ形式**：古典情報（挿入した記憶装置上のファイル、またはデバイス全体）のみ
- **誤操作対策**：制御APIの操作は1台の操作端末に限定する（操作トークンまたはセッション固定等）
- **OS起動用microSDとの分離**：Pi自体の起動ディスクと、ユーザーが投入する記憶装置は物理的に別ポート／別スロットとする

#### FR-03 物理乱数生成

- **取得元**：量子コンピュータ（Qiskit Aerシミュレータ／IBM Quantum実機）のみ
- **量子回路の設計（PQRNG）**：単純な全qubit Hadamardではなく、PQC→H→CHの3ブロックを組み合わせたパラメータ化量子回路（PQRNG）を採用

#### FR-05 破壊的上書き（レジスタ転写・原本消去・点火）

1. **レジスタへの転写**：対象データを、炉内の保護されたメモリ領域（ロックされたRAMバッファ）へ読み込む
2. **原本の消去**：投入された記憶装置そのものを、生成した真の乱数で上書き。デバイス全域の上書きを基本とし、複数パス（最低2パス推奨）でウェアレベリングによる残存を実用上潰す
3. **レジスタの消去（点火）**：レジスタ上のデータを、別途生成した真の乱数でin-place上書きし、参照を破棄する
- **レジスタ実装**：Pythonの不変オブジェクト（`bytes`/`str`）は使わず、`bytearray`または`numpy.ndarray(dtype=uint8)`等のmutableでin-place書き込み可能なバッファのみを使用。`mlock`/`mlockall`でRAMに固定し、OSのswapを無効化（`sudo swapoff -a`）する
- **正直に扱うべき技術的限界**：USBメモリ／SDカードのウェアレベリングにより単純な1回上書きでは元データが別の物理ブロックに残存しうる。UI上でこの限界を説明する固定テキストブロックを消去確認画面に表示する
- **デモ運用**：デバイスサイズが大きいほど全域上書きに時間がかかるため、小容量（数GB程度）のUSBメモリ／SDカードの使用を前提とし、容量ごとの所要時間を事前に計測する

### 2-2. Should機能（デモの説得力を左右する）

#### FR-07 視覚演出

- **部品候補**：高輝度COB LEDテープ、またはWS2812B（アドレサブルLED）を筐体スリットに配置
- **制御**：Raspberry PiのGPIOから`rpi_ws281x`ライブラリ等で制御。MQTTの`furnace/erase_progress`イベントで崩壊過程の明滅パターンを、`furnace/erase_complete`イベントで最大輝度のストロボ発光を実行
- **視認性要件**：明るい会場・距離のある審査員席からも視認できる輝度を、事前に実機で会場相当の照明条件を再現してテストする

#### FR-08 聴覚演出

- **部品候補**：I2S DACモジュール（MAX98357A等）＋小型スピーカー
- **音源制作方針**：既存楽曲の直接使用・酷似した旋律の使用は著作権上不可。「宇宙的・環境音楽的な質感」を参考にとどめ、オリジナルで制作する
- **実装方式**：まず事前制作のアンビエント音源＋崩壊速度連動のホワイトノイズクロスフェード（案A、実装コスト低）で確実に動くものを作り、時間があれば`pyo`/`sounddevice`によるリアルタイム生成（案B）へ発展させる

#### FR-10 儀式的UI/演出モード

- **状態遷移**：`待機 → 投入 → 選択 → 転写 → 原本消去 → 乱数生成中 → 点火（レジスタ消去） → 体感中 → 待機に戻る`
- **実装**：状態機械ライブラリ（Pythonの`transitions`等）またはasyncioベースの自作ステートマシン。各状態遷移のたびにMQTTイベント（`furnace/state`）をpublishし、発熱（FR-06）・光（FR-07）・音（FR-08）・感覚イベント（FR-11）がすべてこの状態機械に従って同期する。早い段階でこの状態機械の骨格だけ先に作り、各機能をそこに接続していく順序を推奨

---

### 2-3. Could機能（時間があれば・加点要素）

#### FR-11 感覚のAPI化（義体化ユーザー対応）（Could・Tier2）

- **アーキテクチャ**：温度・光・音の実測値／演出値を、既存のハードウェア駆動とは独立した配信レイヤーとして、MQTTトピック（`furnace/sensory/heat`, `furnace/sensory/light`, `furnace/sensory/sound`）へpublish
- **ブラウザ受信**：Mosquittoのwebsocketsリスナー（9001番）経由で、ブラウザから`paho-mqtt.js`を用いて直接購読する
- **受信側の実装例**：スマートフォン・タブレットの画面表示（温度・光・音の値をグラフやアニメーションとして可視化）。**振動フィードバックは採用しない**
- **聞こえる周波数帯の調整**：スピーカー出力にソフトウェアイコライザーを実装し、UIから高域寄り/低域寄りのプリセットを切り替えられるようにする

#### FR-12 熱破壊回路（炉の芯、コンデンサ対による物理実装）（Could・Tier2）

技術要件の詳細は[[architecture]]（回路原理の導出）・components.md（部品表・実験手順）を参照。概要のみ：コンデンサ対（相補ペア）による二重井戸回路をRaspberry Pi Picoで駆動し、消去と発熱を同一の物理素子に一致させる。

#### FR-14 物理シミュレーション映像演出（Could）

- **現状**：別リポジトリ（`physical_simulation/information_erasure_visualizing`）で本文書とは別アプローチで開発中。以前このリポジトリで試したthree.js/matplotlibベースの設計は削除済み。別リポジトリでの実装が固まり次第、本節を書き換える
- **本体との同期方針**：MQTTではなくFastAPIのSSEで儀式イベント（select／erase_started／random_acquired／erase_complete）を受信する構成を想定
- **誠実さ・プライバシー**：配信するのはメタデータと統計量（バイトヒストグラム等）のみで、データ本体はネットワークを流さない
- **性能対策**：品質Tier切替、fps低下時の自動縮退、事前レンダリング動画へのフォールバックを必須とする

## 6. 技術的リスクと対策

|リスク|影響するFR|対策|
|---|---|---|
|IBM Quantum実機のキューイング遅延|FR-03|ライブデモでは実機を使わず、シミュレータ（Qiskit Aer）を基本線とする|
|大容量の記憶装置ではデバイス全域上書きに時間がかかりすぎる|FR-05|デモでは小容量（数GB程度）のUSBメモリ/SDカードを使用する前提とし、容量別の所要時間を事前に計測する|
|SSD/USBメモリのウェアレベリングにより物理上書きが不完全|FR-05|デバイス全域への複数パス上書きを主軸とし、UI上でこの限界を正直に説明する|
|レジスタ領域がOSのスワップに書き出される|FR-05|mlock/mlockallとswapoffを徹底し、デモ前にメモリダンプ等で漏出がないことを検証する|
|発熱体による低温やけどのリスク|FR-06, FR-12|ソフトウェア上限温度＋サーマルヒューズの二重の安全機構、温度センサーの継続監視（詳細はcomponents.md参照）|
|同一Wi-Fi上の第三者端末から消去がトリガーされる|FR-01, FR-05|制御APIの操作を1台の操作端末に限定し、実行前の二段階確認を必須とする|
|ブラウザがMQTTを直接購読できず、FR-11の感覚情報配信が動作しない|FR-11, FR-07, FR-08|Mosquittoのwebsocketsリスナーを早期に構築・動作確認する|
|FR-08の音源が既存曲に酷似してしまう著作権リスク|FR-08|「質感の参考」に留め、旋律・フレーズのオリジナル制作を徹底|
|別リポジトリでのFR-14実装が発表までに間に合わない|FR-14|早期に進捗を確認し、間に合わない場合は「筐体本体の機能だけで完結する」という位置づけに切り替える|
