# 忘却炉は抽象イベントを放送するだけで脳への刺激は電脳側が決める

## 要約

忘却炉が脳へ直接はたらきかけることはしない。
炉ができるのは「いまどれくらい消えたか」「どれくらい熱いか」を外へ放送するところまでで、それを身体でどう感じさせるかは受け取った側が決める。
この線引きは運用上の決まりではなく、装置の作りとして越えられないようにする。

## 処理を5段に分け、境界を2つ置く

```
1（忘却炉）  測定。実熱源の温度を実測する
2（忘却炉）  実測温度を抽象的な演出値へ変換する
─── 境界①（装置間・MQTTで放送。炉は以降に一切関与しない） ───
3（電脳側・アプリ）  体験の設計。どこをどんなカーブで温めるか
─── 境界②（アプリはこれ以降を知らないし触れない） ───
4（電脳側・OS）  調停・権限・段から電極への変換・安全予算の執行
5（電脳側・ハードウェア）  瞬時の安全遮断。OSからも上書きできない
```

## 境界を装置の外側に置く

境界①を炉の出口に置くのは、**忘却炉が脳を刺激する権限を、決まりごとではなく構造として一切持たないようにする**ためである。炉は利用者と同意関係を持たない外部の展示装置であり、電脳OSから署名を検証されることもサンドボックスに入れられることもない。そのような装置が実際の刺激を事実上決定する経路は、最初から作らない。忘却炉はアプリケーションですらなく、データを放送するだけの周辺機器である。

この境界は既存の設計とも一致する。感覚配信はもともとハードウェア駆動とは独立した配信レイヤーとして疎結合に設計されており、炉の側は受信側の実装を知らないまま完結する。**忘却炉が電脳側の専用アプリを自前で用意することもしない。** 炉が用意すべきは、実装を知らない第三者のアプリでも解釈できるデータ形式だけである。

境界②を置くのは、個体ごとの較正データと安全パラメータをアプリから隔てるためである。この先の分担は別に定めた。

## 送るのは生の数値ではなく装置非依存の記述

炉が放送するのは、温度計の読みをそのまま流したものではない。強度・持続時間・進行度を持つ構造化されたイベントとして記述し、それを身体のどこにどう当てるかは受信側に委ねる。

この形式には前例がある。音声合成のSSML、触覚のCore Haptics、色のICCカラープロファイルは、いずれも**受信側の事情を知らないまま表現だけを伝える**形式である。炉からアプリへ、アプリからOSへの各段が、生データでも直接命令でもなく宣言的な記述を渡すという同じ形をとる。

## 概念実装で放送する内容

既存のMQTTトピックにそのまま乗せる。消去の進行度（0.0〜1.0）、温度の演出値、儀式の状態、消去完了の通知の四つである。

電脳アプリが使うのは主に進行度で、温感の前線の位置をこれから決める。温度の演出値は強さに充てる。**炉は受信側が何であるかを知らない。** 同じ放送を、画面を見ている人も電脳を持つ人も受け取る。

なお炉が外へ出す情報は攪拌後のパターン・消去ビット数・実測熱量・経過時間に限られ、消去される内容そのものは放送に乗らない。熱のチャネルは内容を漏らさない。

## 受け取る側が何をできるかを申告する

受信側が扱えないものは送らない、という割り切りを明文化する。申告は二段階に絞り込む。OSからアプリへは電極の詳細を伏せた抽象的な能力が渡り、アプリから炉へはさらに粗い宣言だけが渡る。**忘却炉は利用者の脳について何も知らないまま終わる。**

裏を返せば、炉が送った値はアプリが読み替え、OSが変換して電極へ束縛するという三段を経る。出したものがそのまま届くことはないため、**炉の側で「こう感じさせる」と当てにする設計をしてはならない。**
