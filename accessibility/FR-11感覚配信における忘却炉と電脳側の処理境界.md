# FR-11感覚配信における忘却炉と電脳側の処理境界

## 要約

忘却炉が温度などの情報を電脳（BCI）に送るとき、忘却炉は「どれくらい熱いか」という抽象的な値を送るところまでを担当し、それを実際にどう脳に感じさせるかは電脳側に任せる。電脳側でも、どんな体験にするかを決めるのはアプリで、その人の体に合わせて安全に実行するのは基本ソフトという分担にする。ただし全ての情報が別の表現に置き換えられるわけではなく、対応できる相手にしか送れない情報もあることを認めておく。


FR-11（感覚のAPI化）で忘却炉が電脳側へ感覚情報を送る場合、忘却炉側と電脳側のどちらがどこまでの処理を担うかが未定義だった。忘却炉が電脳側の内部実装（個体ごとの電極↔知覚対応表、刺激パラメータ生成、安全域制御）まで意識した設計をしてしまうと、電脳側の実装が変わるたびに追従が必要になり、かつ実際の刺激を外部装置である忘却炉が事実上決定する経路を作ってしまう。加えて[[非侵襲BCI車椅子における処理分担と低帯域幅コマンド設計]]で確認した通り、電脳側の処理は特定アプリケーション専用ではなく汎用アプリに集約される構造になっており、忘却炉が電脳側アプリの中身を知っている前提の設計は将来のエコシステムと整合しない。

## 選択肢と却下理由

**案A：忘却炉が電脳側の内部実装まで意識した専用データを送る。** 却下。[[BCI熱感知書き込みの脳内経路]]で確認した通り島皮質は温度専用チャンネルではなく多モーダルに混線し、[[電気刺激によるBCI書き込みと文字表示]]で確認した通り電極↔知覚の対応表は個体別に作る必要がある。忘却炉がこの較正データを渡される相手ではないのは、原理的に持てないからではなく、利用者と同意関係を持たず電脳OSから署名検証もサンドボックス化もされ得ない外部の展示装置だからである（[[較正データへのアプリアクセスの段階設計]]）。

**案B：単一の普遍的な抽象スキーマだけで全ての受信側（画面・ウェアラブル・将来のBCI）を一律にカバーする。** 却下。動的走査刺激による文字/パターン提示のような、刺激能力そのものに依存する体験は、画面表示への劣化表現を持たない。「画面で見る温度グラフ」と「島皮質を逐次走査される温感」は同じ体験の劣化バージョンではなく別種の体験であり、単一スキーマへの優雅な劣化（graceful degradation）という発想自体が効かない。

**案C（採用）：5層の処理境界＋能力申告による拡張機構。** 下記「構想」参照。

## 構想

処理境界を5層で切り、うち2箇所を硬い境界とする。当初は電脳側を一枚岩として4層で切っていたが、個体較正という機械的変換と、どんな体験にするかという表現の設計を混同していたため改めた。各層の責務の詳細は[[電脳OSが担う責務の範囲]]を参照。

```
Layer1（忘却炉）：測定（実熱源の温度実測）
Layer2（忘却炉）：実測温度に応じた抽象的な演出値への変換（対数スケール変調）
─── 境界①（装置間・furnace/sensory/heat 等としてMQTT publish。忘却炉は以降に一切関与しない） ───
Layer3（電脳側・汎用アプリ）：体験の設計（走査提示か同時提示か、展開カーブ、狙う身体部位）
─── 境界②（アプリはこれ以降を知らない・触れない） ───
Layer4（電脳側・OS）：調停・権限・抽象部位から電極への変換・摩耗分散・累積安全予算
Layer5（電脳側・ドライバ/ハードウェア）：瞬時の安全インターロック（OSからも上書き不能）
```

境界①をLayer2/Layer3の間に置くのは、案Aを却下した理由に加え、`concept/technical_req.md`のFR-11が既に「ハードウェア駆動とは独立した配信レイヤー」として疎結合設計を採用しておりこの境界と一致すること、実際の刺激の実行権を電脳側に残すことで外部の展示装置である忘却炉が本人の同意なく脳を刺激する経路を構造的に作らないという安全・責任分界点として機能することの2点が理由。忘却炉はアプリケーションですらなく外部の周辺機器であるため、脳に対する権限をポリシーとしてではなく構造として一切持たない。

境界②を置くのは、個体較正データと安全パラメータをアプリケーションから隔てるためである。ただしこれを単純な全面禁止とはせず、開示を伴わない経路を既定としたうえで段階的なアクセスを設計する（[[較正データへのアプリアクセスの段階設計]]）。

あわせて、忘却炉が電脳側専用アプリを自前で作る方針も採用しない——忘却炉が用意すべきは、実装を知らない第三者アプリでも解釈できるデータ形式だけである。なお、Layer3以降の分業は[[BCI用ソフトウェア基盤の実装状況]]で確認した通りBCI2000・CorTec Brain Interchange等に実在するが、複数アプリの調停を担う層は現時点でどこにも実装されていない。

Layer2で送るデータは、`furnace/sensory/heat: 42.3`のような生の数値ではなく、SSML（音声合成マークアップ）・Core Haptics（触覚）・ICCカラープロファイル（色）に前例のある「装置非依存の記述＋受信側での変換」という形式を採る（いずれも広く公知の技術としての参照で、本ノートでの一次資料照合は行っていない）。これらの前例は単に装置非依存であるだけでなく、**受信側の機微な情報を開示せずに表現だけを伝える形式**として共通している。忘却炉からアプリへ、アプリからOSへの各段が、データでも直接命令でもなく宣言的な記述を渡すという同じ形をとる。温度の強度だけでなく、[[BCI熱感知書き込みの脳内経路]]が報告する「電極位置が上方に移動するにつれ四肢から体幹・肩へ温かさが広がる」という空間的拡張性を、実測温度に由来する強度と結びつけ、強度・持続時間・空間的拡張度合いを持つ構造化イベントとして記述する。

案Bを却下した理由（劣化不能なコンテンツの存在）に対応するため、基盤層（共通の抽象記述）・能力申告層（受信側が対応機能を忘却炉へ申告する）・拡張層（申告した受信側にだけ追加のリッチな内容を送る）の三層構成を採る。動的走査刺激のように代替表現を持たないコンテンツは、対応デバイスがない場合は単に送らない、という割り切りを明文化する。

能力申告は二段階の絞り込みとして設計する。OSからアプリへは電極の詳細を伏せた抽象能力（局在温感が可能か、走査提示に対応するか）が渡り、アプリから忘却炉へはさらに粗い宣言（拡張度合いを扱えるか、走査グリフを扱えるか）だけが渡る。忘却炉は利用者の脳について何も知らないまま終わる。裏を返せば、忘却炉が送る拡張度合いはアプリの再解釈・OSの圧縮とクリップ・順応補正の三段を経るため、**忘却炉は忠実な再現を前提にしてはならない**。

## 未検証

能力申告プロトコルの具体的な実装（MQTTトピック設計、二段階の申告をどう連鎖させるか、申告のタイミング等）は本ノートでは方針レベルに留まり、実装レベルの検証は未実施。動的走査刺激のような「劣化できないコンテンツ」が本当に他に代替表現を持たないかどうかも、今後の設計次第では反証されうる。忘却炉専用アプリを作らないという判断も、電脳アプリのエコシステムが実際に汎用形へ収束するかどうかという未確定の予測に依存しており、第三者アプリのエコシステムが成立している実例は現時点で確認できていない。Layer3以降の層構造は既存の実装例からの類推を含み、とりわけ複数アプリの調停を前提とした運用は実在しないため、忘却炉の想定する使い方は未成立の前提の上に立っている。

拡張度合いの具体的な算出も未確定である。[[architecture]]の通り忘却炉の接触プレートはアルミの熱拡散により空間的に一様であり、物理的な空間分布そのものが存在しない。したがって拡張度合いは実測可能な物理量ではなく、処理進捗や強度から合成する演出値として扱うほかなく、その合成規則は未定。
